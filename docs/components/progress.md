# `PctProgress` — how far along a task is, or that it is under way at all

**Summary:** How far along a task is — or, when nobody can say, that it is under way at all.
**Entrypoint:** `@pacit/components/progress`
**Selector:** `pct-progress`
**Status:** released
**Category:** Data & status
**ARIA APG pattern:** none — there is no APG pattern for a progress bar. What there is is the
[`progressbar` role](https://www.w3.org/TR/wai-aria-1.2/#progressbar), and this component does
not write it: the bar **is** a `<progress>`, so the role, the bounds, the value and the
indeterminate state are the element's. Named in the class JSDoc.

The whole component is one boundary drawn twice
([0049](../decisions/0049-a-progress-bar-is-the-platforms-element-under-our-paint.md)): the
platform's element for what a reader hears, our own drawing for what an eye sees. It is the
checkbox's shape one component over, and it is here for a measured reason rather than a
stylistic one — `appearance: none` is the price of painting a `<progress>`, and it takes the
engine's indeterminate animation away.

**The host is also the pipe.** The indeterminate band travels from entirely before the groove
to entirely past it, so without a clip it is painted outside the bar for most of every loop —
a stripe crossing whatever stands beside it. The clip is `overflow: hidden` on the host,
carrying the groove's own radius, because the fill cannot be a child of a `<progress>` (the
skeleton, whose sheen is the same drawing, clips at its track instead — there the track is a
`<div>`). It costs exactly one thing, and the cost is measured: an outline is painted OUTSIDE
the box that draws it and a clipping box erases a descendant's outline, so the `CanvasText`
ring that gives the groove its extent under `forced-colors: active` is drawn on the clipping box — the
same rectangle to the pixel — rather than on the `<progress>`. A ring the clipping box draws
itself is untouched by its own `overflow`.

## Usage

```html
<pct-progress [value]="42" ariaLabel="Uploading" />
```

| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Value**   | `value: number \| null`, default `null` = **indeterminate**. Text that does not parse is `null` too. Out of range it is clamped into `[0, max]`, and the clamped number is what the element carries — a reader hears 100%, not 150%.                                                                      |
| **Inputs**  | `value` (`number \| null`), `max` (default `100` — **not** the platform's `1`, see below), `ariaLabel`, `ariaLabelledby`, `size` (`sm \| md \| lg`, from config), `tone` (`PctTone \| null`, default `null`)                                                                                              |
| **Outputs** | none — a progress bar reports, it does not emit. What changes the value is the task, and the task is the application's.                                                                                                                                                                                   |
| **Slots**   | none — the bar draws a groove, a fill and, when it has a tone, a mark. The sentence beside it ("Copying files", "129 of 256") is the consumer's, and it is also what `ariaLabelledby` should point at.                                                                                                    |
| **Parts**   | `bar` (the box that clips — the groove and the fill live in it), `track` (the `<progress>` itself, which is the groove), `fill` (the sibling drawn over it — the value in the determinate state, the travelling band in the indeterminate one), `icon` (the tone's mark, drawn only when there is a tone) |
| **Harness** | `PctProgressHarness`                                                                                                                                                                                                                                                                                      |
| **Tokens**  | the `--pct-progress-*` prefix plus eleven entries in `contrast.policy.json` (three untoned, two per tone)                                                                                                                                                                                                 |
| **Strings** | **none.** The first component in five to add nothing to `PCT_TEXTS` and therefore nothing to every other entrypoint's bytes — it draws no text at all.                                                                                                                                                    |

**The tone is two channels, and the second one is why it took a decision rather than a
stylesheet.** `tone` says what the work IS — a failed upload is `danger` at whatever percentage
it stopped at, a finished one is `success` at 100 — and it draws in two places at once: the
fill's colour, and a mark the library draws beside the bar. Never the colour alone. A bar that
turns red says nothing to a reader who does not separate red from green, and nothing at all
under `forced-colors: active`, where the fill is `Highlight` whatever the author asked for
([`req-a11y-forced-colors`](../requirements/a11y.md#req-a11y-forced-colors)). The mark is the
half that survives both, and it is `PctIconName`'s — a consumer's own icon set replaces it like
any other drawing ([0011](../decisions/0011-icons.md)).

Three consequences worth stating plainly. **An untoned bar is unchanged**: no attribute, no
mark, and the same geometry it had before tones existed. **A toned bar is as tall as its mark**
(16 px), because the mark stands beside the groove rather than inside it — the clipping box
moved off the host onto `bar` for exactly that reason. **An indeterminate bar may carry a tone**:
"retrying, and the last attempt failed" is a real state, and nothing here pretends to know what
the work will do next.

**Why `max` defaults to 100 and not to the platform's 1.** Which mistake each default produces
decides it. With `max="1"` a consumer writing `[value]="40"` gets a **full** bar, because the
element clamps — a wrong answer wearing the look of a finished task. With `max="100"` the
mirror-image slip (`[value]="0.4"` meaning four tenths) draws an almost empty bar, which is
visibly wrong and fixed in seconds. The element never sees the difference: `max` is always
written out.

**Why there is no default accessible name.** A progress bar's name is _what_ is progressing,
and only the application knows that. A default of "Progress" would satisfy axe's
`aria-progressbar-name` rule and tell a screen-reader user nothing — a gate passing on our own
echo. Instead the component reports a bar with neither `ariaLabel` nor `ariaLabelledby` in dev
mode, the same way `pct-drawer` reports an unnamed panel.

## Decisions this component implements

[0049](../decisions/0049-a-progress-bar-is-the-platforms-element-under-our-paint.md) (the main
one — why the element, what `appearance: none` costs, why the fill is a sibling, why the band
is an element and not a gradient),
[0039](../decisions/0039-a-state-the-platform-publishes-is-not-ours-to-write.md) (no
`aria-valuenow` of ours beside the element's own),
[0034](../decisions/0034-multiplicity-is-a-tag.md) (a circular indicator would be a tag, not a
`variant` input).

## Known limitations

- **No circular variant.** A ring is a different drawing with its own tokens, and one already
  exists inside `pct-button` for a button that is working. A standalone one is a tag of its
  own when somebody needs it.
- **No buffer or second value.** The platform's element has one value. A media player's
  buffered range is a second bar, and this component does not pretend to be two.
- **A tone is not announced.** It reaches the eye and no further: `pct-icon` is `aria-hidden`,
  so a screen-reader user hears the `<progress>` and the consumer's own sentence beside it and
  nothing about success or failure. If a tone has to be heard, it belongs in that sentence —
  which is what `ariaLabelledby` points at — and not in a string this component invented
  (0039). _Until 2026-09-07 this row said there were no tones at all, and the reason it gave
  was the right one: the second channel is an icon, four names into `PctIconName` at once, and
  a set no single component could judge. Two components wanted the same four, which is what
  plan 4.14 said would happen._
- **Nothing is announced.** A determinate bar that spoke every percent would be noise, and the
  role is one assistive technology polls. An application that needs "upload complete" said out
  loud has a sentence to announce, and the sentence is not the bar.
- **The name is required and nothing enforces it at build time.** A consumer who supplies
  neither `ariaLabel` nor `ariaLabelledby` gets a dev-mode warning and an axe violation on
  their own page; this repository's static gate can only see its own templates.
