# Requirements — accessibility

This area absorbed the built-in semantics requirement
([`req-a11y-built-in`](#req-a11y-built-in)), which used to sit among the API ones. Two went
the other way, because they are about **gates**, not accessibility: the negative-control
rule is [`req-quality-negative-control`](quality.md#req-quality-negative-control) and the
hydration gate is [`req-quality-hydration`](quality.md#req-quality-hydration).

> The shape of an entry and the meaning of the **Gate** / **Control** fields are described
> in the [README](../README.md#requirement-shape).

---

### <a id="req-a11y-wcag"></a>`req-a11y-wcag` — WCAG 2.2 AA as the minimum

**Promise.** Components meet WCAG 2.2 level AA as a minimum; where possible we aim higher.

**Gate:** [`req-a11y-axe`](#req-a11y-axe) (the rendered DOM) +
[`req-token-contrast`](tokens.md#req-token-contrast) (the values in the palette) — two
different layers of the same requirement
**Control:** see both gates above

> **Formal conformance does not mean good quality.** The first axe audit found no
> violations, and the `target-size` rule **passed** on an 18×18 px hit area — because SC
> 2.5.8 allows a spacing exception ([`lesson-14`](../lessons.md#lesson-14)). Hence
> [`req-a11y-touch`](#req-a11y-touch) is a separate, stricter requirement.

### <a id="req-a11y-built-in"></a>`req-a11y-built-in` — Accessibility built into the component

**Promise.** ARIA is managed internally, identifiers come from a util (`nextPctId`), CDK
a11y (`FocusMonitor`, `FocusTrap`) is used where it is needed. **CDK types never leak into the
public API** — the mechanics are CDK's, the contract is ours. Taking a mechanic is a
measurement and not an assumption: `LiveAnnouncer` was named here until D4 and is **not** used,
because it hides its element with a class from a stylesheet this library never asks a consumer
to include, and unhidden it paints every announcement across the page
([`lesson-83`](../lessons.md#lesson-83), [0026](../decisions/0026-one-channel-per-politeness.md)).

**A change nobody is pointed at is announced, and from one place.** The document carries two
live regions — one `polite`, one `assertive` — for the whole library rather than one per
component, they are in the document before anything is said, and a channel does not repeat what
it is already saying. What is drawn on the screen announces from where it is drawn instead: a
validation message is `role="alert"` on the text the user can read, which is one owner for one
sentence ([`req-api-message`](api.md#req-api-message)). The first consumer of the channel is
the select's empty panel — focus stays on the trigger, an empty listbox gives
`aria-activedescendant` nothing to name, and the sentence inside the panel would otherwise
reach the eye alone. The text is the library's own, so it comes through `PCT_TEXTS`
([`req-api-texts`](api.md#req-api-texts)) and is announced in the application's language.

**The name is reachable from the host.** A consumer writes attributes on the tag they type
and on nothing else, so where the role does not sit on the host element the component takes
the name as `ariaLabel` / `ariaLabelledby` inputs and forwards it to the element that has the
role. An ARIA name on a roleless host is prohibited and read by nobody, ours as much as
theirs. A panel opened by a control has a **default** name before either input is reached for:
the control itself, by id — which is what the APG's own menu-button example does and what makes
a menu announce the two words already on the screen rather than "menu".

**Structure inside a list is a relation, not a drawing.** A heading over part of a list is a
`role="group"` named by the very element the eye reads (`aria-labelledby`), and the options
below it are still owned by the listbox through it — `option` names `group` and `listbox` as
its context and `listbox` names `group` and `option` as what it may own, so the group is the
one wrapper that may stand between them. Everything else about the list stays one list: the
walk, the numbering, `aria-activedescendant` and the typed prefix cross the headings, because
a heading is something the user reads and not somewhere the user can be.

**How many answers a list takes is the listbox's to say.** A many-choice list carries
`aria-multiselectable` on the listbox and `aria-selected` on **every** option under it — the
false half is the part a single-choice panel never has to say, and it is what tells a reader
that a row it is standing on could be chosen. The eye is told twice on purpose: a chosen row
takes a surface AND a mark, because several chosen rows plus the keyboard cursor are three
states in two backgrounds, and in forced-colors mode the substitution leaves them fewer than
that. The mark says nothing to a reader (`aria-hidden`) — `aria-selected` has already said it
([0034](../decisions/0034-multiplicity-is-a-tag.md)).

**A trigger that can be typed into is a different element, and one control all the same.** The
APG has two combobox patterns and this library implements both on one component: select-only,
where the trigger is a `<button>`, and editable with list autocomplete, where it is an
`<input>` carrying `aria-autocomplete="list"`. They are the two branches of one conditional, so
exactly one is ever in the tree — which is a thing a gate has to be able to tell from two named
elements standing side by side, and `check-aria` now counts naming carriers per DOM state
rather than per file. Focus stays on the trigger in both, so the panel is still pointed at and
never entered ([0035](../decisions/0035-a-filter-is-a-question-not-a-value.md)).

**A control the mouse can reach is one the keyboard can reach, and the two need not be the
same control.** The select's cross is out of the tab order — a `<button>` with `tabindex="-1"`,
so a reader's virtual cursor still finds and presses it while Tab walks past — and that is a
measurement of the platform rather than a saving: the one clear control a browser draws by
itself, in `<input type="search">`, is in no engine's tab order either, and where the platform
gives the keyboard a road to the same thing that road is Escape. So the keyboard's cross is
Escape over a shut panel, and it is **spent only when it did something**: a control with
nothing to take back leaves the event alone, so the key travels on to the dialog the select may
be standing in ([0036](../decisions/0036-a-clear-takes-back-what-the-trigger-shows.md)).

**A container whose content has not arrived says so, and that is what makes it legal.** A
`role="listbox"` with no rows in it is not merely a bare panel: `listbox` is one of the roles
ARIA declares with required owned elements, and an audit reports the empty one as a
**critical** `aria-required-children` — from the listbox itself. The state the specification
has for exactly this is `aria-busy`, and it is the whole repair: a container marked busy is one
whose content has not arrived, so the rule waits with it
([`lesson-106`](../lessons.md#lesson-106)). It goes on the listbox and on nothing else, because
it is the listbox's content that is late — a shut panel is not a stale reading of anything —
and while it is up beside rows from an earlier answer it is what says they may not be the last
word. The sentence such a panel carries is a **third** one, and it is not a phrasing of the
other two: "no options" and "no matches" are conclusions, and a request in flight has reached
neither ([0037](../decisions/0037-loading-is-a-fact-about-the-list.md)).

**A cursor names a row, and a list that arrives twice is two instances of one list.** Where
`aria-activedescendant` is the whole of what a reader is pointed at, an index kept as a number
is a promise only a list that never changes can keep: a server's answer replaces the rows on
nobody's keystroke, and the attribute then names an id nothing in the document carries — which
is silence for the reader and a row nobody pointed at for `Enter`. So the walk puts the cursor
back on the entry it was standing on, by the same test that maps a value back to an option
([`lesson-107`](../lessons.md#lesson-107)).

**A set the DOM does not hold has to say how long it is.** Where a panel draws only the rows it
can show, every option carries `aria-setsize` and `aria-posinset` — the pair ARIA has for
exactly this, a set whose elements are not all present. It is the one promise on this page that
**no audit asks for**: axe has no rule about either attribute, so a windowed listbox that says
neither is green and tells the user a five-thousand-row list has eleven rows in it. The
numbering is the list's and not the group's, because that is what the walk, the ids and
`aria-activedescendant` already count in. Two structural things go with it and are not
decorations of it: the element that **scrolls** is the listbox itself, since the exemption
keeping a panel of unfocusable rows out of `scrollable-region-focusable` is written for a
combobox's own popup — one element in and the same tree is a serious violation — and the space
the undrawn rows would have taken is a **pseudo-element**, because padding does not scroll and
any spacer element is a child the listbox does not own
([0038](../decisions/0038-a-window-is-measured-and-its-spacer-is-not-an-element.md)).

**Where focus goes is the role's answer, not the library's.** Two panels of options here walk
their list differently and it is written down as a choice
([0032](../decisions/0032-a-menu-moves-focus-a-listbox-points-at-it.md)): a combobox keeps DOM
focus on the trigger and names the active option with `aria-activedescendant`, because the user
is editing a value; a menu gives DOM focus to the row, because the row is the whole of what the
user is on. Each road brings a bill — the first pays for it with `PctFocusStays`
([`lesson-18`](../lessons.md#lesson-18)), the second with a tab order that has to be answered
([0031](../decisions/0031-a-panel-s-tab-order-belongs-to-its-trigger.md)).

**Write ARIA for what the element does not already say.** A role put on a native element does
not take the element's states with it: `role="switch"` over an `<input type="checkbox">` keeps
its checked state from the element's own checkedness, and an `aria-checked` written beside it
is **ignored** — measured in three engines and read out of Chromium's own accessibility tree,
where a checked box carrying `aria-checked="false"` still comes out checked. So the switch
writes none, and its cases assert the ABSENCE, because the absence is the promise: an attribute
that cannot be wrong is one that can drift with nothing to notice
([`lesson-112`](../lessons.md#lesson-112)). The same role on an element with no such state —
a `<button>`, a `<div>` — is a **critical** `aria-required-attr` in all three, which is what
decides the element rather than any preference for the native road
([0039](../decisions/0039-a-state-the-platform-publishes-is-not-ours-to-write.md)). Where the
specification allows a state the platform cannot express, the gate is the **type**: `switch`
has no `mixed`, no audit says so, and `PctSwitch` therefore has no `indeterminate` input for
anybody to ask with.

**A message that appears announces itself, from where it is drawn.** A validation message
enters the DOM with focus somewhere else entirely, so the text the user can read has to BE the
live region that speaks it — `role="alert"` on the error part, one owner for one sentence,
rather than the shared channel repeating what is already on the screen
([0026](../decisions/0026-one-channel-per-politeness.md)). Four templates did that and nothing
measured them, which is the shape of [`lesson-65`](../lessons.md#lesson-65): the fifth
component to draw a message would have announced nothing and the run would have stayed green.

**Gate:** `libs/components/*/src/*.spec.ts` — ARIA relations checked per component;
`apps/sandbox-e2e/src/a11y.spec.ts` — an audit of the rendered DOM;
`tools/check-aria.mjs` (target `check-aria`) — the name reachable from the host, the
description naming one message ([`req-api-message`](api.md#req-api-message)) and, at point 7,
the error part carrying the live region that speaks it, over every template of the library, so
a component nobody has written yet is covered from its first commit;
`libs/components/switch/src/switch.spec.ts › never writes aria-checked` plus
`apps/sandbox-e2e/src/switch.spec.ts › the control is a switch whose state is its own
checkedness` — the attribute's absence asserted on both floors, and the accessible tree read
in three engines to say what stands in its place; `libs/components/core/src/core.spec.ts › PctAnnouncer` — one region
per politeness, opened by a render, empty, and a sentence written once;
`apps/sandbox-e2e/src/select.spec.ts › the empty panel` — the same in three engines, plus the
measurement of the defect beside it (with the panel open the trigger points at nothing and is
described by nothing) and the region's own box, which is how a stylesheet promise like
`lesson-83`'s would be caught here; `apps/sandbox-e2e/src/a11y.spec.ts › "a filtering combobox with a
narrowed panel has no violations"` — audited **whole-page** rather than scoped to the panel,
because `aria-controls` and `aria-activedescendant` cross from a trigger in the page to a
listbox in the overlay container, and a reference to an id that is not in the document is
exactly what `aria-valid-attr-value` reports;
`apps/sandbox-e2e/src/a11y.spec.ts › "a control with a cross beside its trigger has no
violations"` plus `select.spec.ts › a cross that takes the answer back` — the named button
standing beside the trigger in a page that was really parsed, Tab walking past it, and the
24 px target measured rather than declared;
`apps/sandbox-e2e/src/select.spec.ts › headings in the
list` plus `a11y.spec.ts › "an open panel with headings has no violations"` — the grouped
listbox measured where it can be wrong, that is in the rendered tree: a heading naming its own
group, an option's owner read off its parent, and one walk across the headings;
`apps/sandbox-e2e/src/select.spec.ts › more than one answer` plus `a11y.spec.ts › "an open
panel that takes many answers has no violations"` — the many-choice listbox beside the
single-choice one, which is where `aria-multiselectable` is measured as a **difference**
rather than as an attribute somebody wrote;
`apps/sandbox-e2e/src/a11y.spec.ts › "a panel waiting for its list has no violations"` plus
`select.spec.ts › a list that is still coming` — the EMPTY listbox, which is the one state of
this panel no case had ever audited, and the cursor measured where it can be wrong: an id read
off the trigger has to name a row that is really in the document after the list underneath it
was answered a second time;
`apps/sandbox-e2e/src/a11y.spec.ts › "a panel drawing a window of a long list has no
violations"` plus `select.spec.ts › a window over a list nobody scrolls to the end of` and
`apps/sandbox-e2e/src/select.spec.ts › a list too long to draw` — a panel drawing eleven rows of
five thousand and scrolled into the middle of them, where the audit measures what it has a rule
for (the listbox is still the element that scrolls) and the cases measure what it has none for
(`aria-setsize`, `aria-posinset`, and a name that points only at a row somebody drew)
**Control:** `a11y.spec.ts › "the a11y gate really does detect violations (a control of the
gate)"`; `tools/check-aria.fixtures/` — 14 prepared inputs, each rejected on its own point, the
newest of them an error part drawn with **no live region on it**, which every other point of
that gate passes over unchanged; before it, two named triggers standing **side by side** where
the reference input has the same two on the branches of one `@if` — with the branch distinction
disarmed the reference input itself stops passing, which is what says the widening did not turn
into a shrug.
For the grouped listbox, two recorded runs: `role="group"` taken off the wrapper leaves the
audit red with a **critical** `aria-required-children` — and it is reported from the LISTBOX
("element has children which are not allowed: `div[aria-labelledby]`") rather than from the
option, so what the audit measures is the owner and not the owned; the row numbering restarted
inside each group leaves five unit cases red, the numbering being what the walk, the ids and
`aria-activedescendant` all stand on.
For the waiting panel, three recorded runs: `aria-busy` taken off the listbox leaves the audit
red with a **critical** `aria-required-children` ("Required ARIA children role not present:
group, option"), reported from the listbox — so what the attribute buys is measured and not
argued; a `loading` that disables the trigger, as `pctButton`'s does, leaves **eight** unit
cases red, because a disabled trigger cannot be opened at all; and a cursor kept as a number
leaves seven cases red across the walk and the control, three of them about an
`aria-activedescendant` naming nothing.
For the window, four recorded runs. `aria-setsize` and `aria-posinset` dropped from a windowed
row leave **two** unit cases and **two** e2e cases red and the audit **green** — that last half
being the whole reason the promise is written above rather than left to axe. The scroll moved
one element in, off the listbox and onto a wrapper that scrolls, is a serious
`scrollable-region-focusable` reported by axe over the tree itself, which is what refused the
CDK's viewport
([0038](../decisions/0038-a-window-is-measured-and-its-spacer-is-not-an-element.md)).
`aria-activedescendant` left naming a row outside the window leaves one unit case and one e2e
case red. And the tolerance taken out of the geometry comparison leaves **Firefox** red with

([`lesson-111`](../lessons.md#lesson-111)) — while a fifth run deleted a repair rather than

([`lesson-109`](../lessons.md#lesson-109)).

### <a id="req-a11y-touch"></a>`req-a11y-touch` — Touch target ≥ 24×24 px, outright

**Promise.** SC 2.5.8 is met **outright, not through the spacing exception**. The hit area
is independent of visual size — an 18 px checkbox box gets an enlarged, centred hit zone.
The value lives in the `--pct-target-min` token.

**Gate:** `apps/sandbox-e2e/src/field-hitarea.spec.ts`,
`apps/sandbox-e2e/src/checkbox.spec.ts` — measuring `getBoundingClientRect()` of the hit
zone, not of the visual element
**Control:** the gate has two documented runs in which it fired:
[`lesson-25`](../lessons.md#lesson-25) (a wrapped select: 19.6 px) and
[`lesson-14`](../lessons.md#lesson-14) (an 18×18 px checkbox passing the axe audit)
**Lessons:** [`lesson-14`](../lessons.md#lesson-14), [`lesson-25`](../lessons.md#lesson-25)

### <a id="req-a11y-axe"></a>`req-a11y-axe` — Automated axe-core audit

**Promise.** An axe-core audit in e2e with the WCAG 2.0/2.1/2.2 tags at levels A and AA, run
on **every view separately** and on the special states (a panel with a scoped theme, a form
in error, an indeterminate checkbox, a dark stage).

**Gate:** `apps/sandbox-e2e/src/a11y.spec.ts`
**Control:** `a11y.spec.ts › "the a11y gate really does detect violations (a control of the
gate)"` — it injects obvious defects, requires them to be found, and checks that the
number of rules that ran is plausible
**Lessons:** [`lesson-14`](../lessons.md#lesson-14), [`lesson-33`](../lessons.md#lesson-33)

> The audit **complements** the token contrast gate, it does not duplicate it: the gate
> measures values in the palette, axe measures the actually rendered DOM (roles, ARIA
> relations, contrast after the layers are composed). Its reach equals the reach of the
> [sandbox](quality.md#req-quality-views): **a gap in what is shown is a gap in coverage,
> invisible in the report because the report is green**
> ([`lesson-33`](../lessons.md#lesson-33)).

### <a id="req-a11y-motion"></a>`req-a11y-motion` — Reduced motion is a token axis, not a rule in a stylesheet

**Promise.** Motion durations are carried by the `--pct-motion-transition-duration` and
`--pct-motion-loop-duration` tokens; `motion.reduced.json` is a separate set of values,
emitted inside a `@media (prefers-reduced-motion: reduce)` block. The preference governs
**all** components from one rule, and a new component inherits it just by using the token.

**Gate:** `apps/sandbox-e2e/src/preferences.spec.ts` — the axis itself, in the browser;
`apps/sandbox-e2e/src/tooltip.spec.ts` — the axis read by a component that really moves: the
tooltip's enter and leave, with the reduced duration measured on the panel and the leave still
ending. That case is where `0.01ms` rather than `0s` stops being a note and becomes the reason
the panel is ever detached — the wait for the leave reads the duration it is given
(`pctAfterTransition`), and a zero that emitted no `transitionend` would leave the overlay
attached;
`tools/check-styles.mjs` point 9 — its readers: a duration in a component sheet comes from
`var(--pct-motion-*)` (rule `literal`), and the preference is answered by the token build
rather than by a sheet of its own (rule `query`). The two measure different halves and neither
answers for the other — a component that writes `150ms` by hand leaves the axis exactly as
correct as the e2e finds it, and stops reading it
**Control:** `preferences.spec.ts › "with no preference the motion axis stands at its
base values"` — comparing the **pair**: without the preference exactly `150ms`, with it exactly
`0.01ms`. The reduction test on its own would pass on a base value read as "little enough"
([`lesson-38`](../lessons.md#lesson-38)). For point 9,
`tools/check-styles.fixtures/duration-literal` and `.../motion-query-in-a-sheet`, each rejected
on its own rule — the second one passes the first rule, which is why it names the rule it
proves
**Decision:** [0008 — the motion axis in tokens](../decisions/0008-motion-axis.md)
**Lessons:** [`lesson-38`](../lessons.md#lesson-38)

> The split follows the **kind of motion**, not its speed: a state transition should
> disappear (`0.01ms` — not `0s`, so that `transitionend` is not lost), while a continuous
> indicator should merely slow down (600 ms → 1500 ms). A stopped spinner would stop saying
> that the button is working — "less motion" must not mean "less information".

### <a id="req-a11y-forced-colors"></a>`req-a11y-forced-colors` — Forced colours mode

**Promise.** Under `forced-colors: active` no state is carried by **colour alone**. States
are rewritten onto system palette keywords; `forced-color-adjust: none` is forbidden,
because it takes the user's palette away from them.

| role               | palette                                                                    |
| ------------------ | -------------------------------------------------------------------------- |
| control surface    | `Field` / `FieldText`                                                      |
| panel surface      | `Canvas` / `CanvasText`                                                    |
| focus              | `Highlight`                                                                |
| selected list item | `SelectedItem` / `SelectedItemText`                                        |
| disabled           | `GrayText`                                                                 |
| marks (tick, dot)  | text colour — the state is carried by their **presence**, not their colour |

**Gate:** `apps/sandbox-e2e/src/forced-colors.spec.ts` — what the browser paints; and
`tools/check-styles.mjs` (target `check-styles`, in CI) — point 7: no declaration of the
mode is **outranked** by a base rule of the same sheet. `@media` adds no specificity of its
own, so a rule of the mode wins by its own selector alone; a block that spells the more
specific state out itself is not reported
**Control:** emulation goes through `page.emulateMedia()` in the `visit()` helper, and the
test **checks `matchMedia` first** — that is, it asks the browser whether it is in the mode
being measured at all. The idiomatic `test.use({ forcedColors })` silently did nothing
([`lesson-38`](../lessons.md#lesson-38)). For point 7:
`tools/check-styles.fixtures/forced-colors-outranked/`, plus a run against the repository —
the button's rule shortened back to `:host([disabled])` fires by name. **The two gates do not
overlap:** chromium and firefox substitute the colours themselves, so a rule of the mode that
never applies leaves every e2e assertion unchanged, and the one engine that would show it runs
none of this file (`browsers.policy.json` — webkit does not have the mode). The e2e run says
what the browser paints; whether the sheet's rules are the reason has no other witness
([`lesson-70`](../lessons.md#lesson-70))
**Lessons:** [`lesson-38`](../lessons.md#lesson-38), [`lesson-40`](../lessons.md#lesson-40),
[`lesson-70`](../lessons.md#lesson-70)

> We do not list borders — the browser forces `ButtonBorder` on them itself. Where one
> channel is not enough, states are split into two independent ones: in the list panel
> selection is carried by the background (`SelectedItem`) and the keyboard cursor by the
> outline (`Highlight`).
